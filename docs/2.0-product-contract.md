# HoverNet 2.0 product contract

## Purpose

HoverNet 2.0 is the first supported, polished Windows and Linux release of the
existing game. It stabilizes the proven client-relay architecture and classic
content pipeline; it is not an engine rewrite.

## Supported player experience

A supported installation must let a new player, without a source checkout:

1. start the game and choose a valid player name;
2. configure display, audio, and remappable keyboard or controller input;
3. select a bundled track, lap count, weapons setting, and hovercraft;
4. complete a local race and view the result;
5. browse the online lobby, host a race, join by race ID, chat, race, and leave;
6. recover to a usable menu after a rejected request, server outage, or missing
   resource, with a specific error instead of a hang or abrupt exit.

Windows and Linux must expose the same core flows and interoperate in the same
race. Platform-native packaging and filesystem locations may differ.

## Supported platforms

- Windows: 32-bit client built with Visual Studio 2022 and the v143 toolset.
- Linux: x86-64 SDL2 client and RaceServer distributed as Debian packages.
- RaceServer: Linux production deployment; Windows remains a development and
  interoperability target until a supported Windows server package is defined.

Exact operating-system versions will be fixed before the first 2.0 beta and
must match the versions exercised by CI and manual release testing.

## Compatibility contract

- Every bundled classic `.trk` and `ObjFac1.dat` resource used by 2.0 remains
  loadable. Malformed or missing assets fail with a named error.
- A 2.0 client and server negotiate an explicit protocol version before lobby
  or race commands. Unsupported versions are rejected with a bounded response.
- Legacy pre-negotiation clients may be supported by a separately tested
  compatibility mode, but must never be mistaken for a negotiated 2.0 client.
- The 2.0 wire format retains the working server-relay gameplay model.
  Server-authoritative physics is out of scope.
- Unknown messages, oversized frames, invalid state transitions, and invalid
  string or numeric fields are rejected without terminating the server.
- Saved settings are migrated or reset field-by-field; a corrupt setting may
  not prevent the application from starting.

## Quality gates

- All supported local and online race flows have automated coverage or a named
  manual test case.
- Windows-to-Windows, Linux-to-Linux, and Windows-to-Linux races complete.
- A two-hour client session has no crash, hang, or continuing memory growth.
- A 24-hour RaceServer soak with repeated joins, races, disconnects, and bad
  traffic has no crash, deadlock, or orphaned race.
- Clean-install packages contain every required runtime asset.
- No known crash, hang, data-loss, or remotely exploitable defect remains.

## Explicit non-goals

Accounts, rankings, matchmaking, progression, authoritative physics, replays,
spectating, mobile/console ports, and a renderer or track-editor rewrite are
deferred beyond 2.0.

## Decisions still required

- Minimum Windows, Debian, and compatible distribution versions.
- Whether pre-2.0 network clients receive a compatibility window or a clear
  mandatory-upgrade rejection.
- Stable per-user settings paths and migration behavior on each platform.
