## Known asymmetries and risks

- The Windows client retains MFC-era UI paths while Linux implements its active
  menus in the SDL2/ImGui player; behavior can diverge even when both compile.
- Linux has substantially broader automated runtime coverage than Windows.
- Runtime asset lookup can still depend on repository-relative paths.
- The Visual Studio solution and project configurations currently target
  Win32/x86. Moving to x64 requires coordinated client, RaceServer, compiler,
  object plug-in, dependency, installer, and CI changes rather than only adding
  an `x64` solution configuration.
- The active RaceServer identifiers and simulation state are now explicitly
  encoded, but persistence and less-common protocol boundaries still need an
  audit for native sizes and pointer-width assumptions.
- The server creates a UDP socket, and legacy peer-to-peer/UDP code remains,
  but current RaceServer gameplay is relayed over client TCP connections.
- `GameSimulation` and related server-authoritative code are scaffolding, not
  the production race authority.

## Phase 1 audit checklist

- Exercise every row above on a clean Windows and Linux installation.
- Record the exact settings path, defaults, and corrupt-file behavior.
- Record asset lookup order from installed package and development checkout.
- Capture idle and active frame-time/memory baselines on both clients.
- Convert each observed difference into a test or a tracked acceptance item.
- Inventory pointer-to-integer casts, ABI-sensitive plug-in interfaces,
  native-layout persistence, and availability of x64 third-party libraries
  before enabling the first Windows x64 build.
